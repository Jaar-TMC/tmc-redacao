<objective>
Implement keyset pagination on the backend: cursor encode/decode helpers, seek predicate in the article filter builder, dual-mode query (cursor vs OFFSET) in get_articles_with_urgency, and cursor response fields in the API handler.

Purpose: Eliminate O(N) OFFSET row-scanning on deep pages. With keyset seek, page 50 performs the same as page 1 because the WHERE clause uses the existing covering index for an O(1) index seek.

Output: Backend returns `nextCursor` and `prevCursor` in GET /api/articles responses. When a `cursor` query param is provided, the query uses keyset seek instead of OFFSET. Score-ordered queries permanently use OFFSET (PAG-03). The `total` count remains stable across cursor-navigated pages (count query uses filter-only WHERE, not the seek predicate). All behavior verified by unit tests.
</objective>

    Add these two standalone functions near the top of `database.py` (after the imports, before the `class ConnectionPool`):

    ```python
    import base64
    # (datetime and uuid already imported in the file)

    def encode_cursor(published_at: datetime, article_id) -> str:
        """Encode cursor as opaque base64 token. Per D-01."""
        raw = f"{published_at.isoformat()}|{str(article_id)}"
        return base64.urlsafe_b64encode(raw.encode()).decode().rstrip("=")

    def decode_cursor(cursor_str: str) -> tuple:
        """
        Decode cursor. Returns (published_at: datetime, id_str: str).
        Raises ValueError on invalid format -- caller falls back to page=1.
        """
        # Re-add padding stripped during encode
        padded = cursor_str + "=" * (4 - len(cursor_str) % 4) if len(cursor_str) % 4 else cursor_str
        raw = base64.urlsafe_b64decode(padded.encode()).decode()
        parts = raw.split("|", 1)
        if len(parts) != 2:
            raise ValueError(f"Invalid cursor format: {cursor_str!r}")
        published_at = datetime.fromisoformat(parts[0])
        id_str = parts[1]
        return published_at, id_str
    ```

    **CRITICAL FIX -- COUNT(*) OVER() must use filter-only WHERE, not seek predicate:**
    The existing `COUNT(*) OVER()` window function in the SELECT counts rows matching the WHERE clause. If the seek predicate is in the WHERE clause, `total` would shrink as the user navigates deeper (only counting rows after the cursor position). This breaks the D-03 response shape guarantee -- `total` and `pages` must remain stable across all pages.

    **Solution:** Call `_build_article_filters` TWICE when `use_cursor=True`:
    1. First call WITHOUT cursor params -- produces filter-only WHERE for the COUNT query
    2. Second call WITH cursor params -- produces filter+seek WHERE for the main data query
